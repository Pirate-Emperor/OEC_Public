### 2. Read-only inspection of DeepSeek cache and quota telemetry

The live OEC revision on the runner was `081aaf34f6379873bdc925d1dcf6b9c3d50349d3`. Its pre-existing working-tree changes were recorded and preserved.

The configured model root was `/nlsasfs/home/lmedge/rahkus/aireos_models`, and the actual Hugging Face hub cache was:

```text
/nlsasfs/home/lmedge/rahkus/aireos_models/hub/models--deepseek-ai--DeepSeek-R1-Distill-Llama-8B
```

The cached snapshot had:
- A `refs/main` entry resolving to snapshot `6a6f4aa4197940add57724a7707d069478df56b1`.
- Config, tokenizer, generation config and safetensors index.
- Two safetensors shards totaling approximately 16.06 GB, with no broken symlinks observed.
- `AutoConfig` and `AutoTokenizer` loaded successfully with offline-only Transformers calls.

**Root cause:** `core_config.py` sets `HF_HOME=SYSTEM_DIRS["models"]`; Hugging Face's hub cache in this environment is under `SYSTEM_DIRS["models"]/hub`. In `brain.py`, the call to `snapshot_download(..., local_files_only=True)` passed `cache_dir=SYSTEM_DIRS["models"]`. That lookup fails to resolve the already-cached snapshot. Because the broad `except Exception` then treats the failure as an incomplete cache, it enters the storage admission branch and requires fresh quota telemetry. The message “Model cache incomplete” therefore did not demonstrate that the actual weight files were missing.

The admission snapshot configured in `storage_config.json` was `~/.cache/aieros/quota_snapshot.json`, with a maximum age of 900 seconds. The diagnostic found that file absent. This is a real admission prerequisite when downloads are necessary; the correction does not bypass it.

Evidence: [offline cache verification](https://github.com/Killer4K-N/Connector_1/actions/runs/37924973497).

### 5. Worker command, GPU selection and purge/synchronization diagnosis

The previous suggested command was:

```bash
python worker_ltx_video.py --gpus 0,1,2,3 --cluster-gpus 11 --no-purge
```

The inspected connector-1 runner only exposed GPU IDs `0` and `1`, so `0,1,2,3` is invalid for this runner. The `cluster_gpus > 1` branch in `worker_process` called distributed `ClusterPurgeManager.sync_and_purge` regardless of `should_purge`, even when `--no-purge` was provided. That branch could purge shared model-cache entries and could block waiting for a cluster-wide participant count; `--no-purge` therefore was not a sufficient protection. This command was inspected but **not launched**.

The candidate fix:
- Routes distributed purging through a helper that requires both `cluster_gpus > 1` and `should_purge`.
- Explicitly skips the cluster purge/wait branch for `--no-purge`.
- Discovers actual physical GPU IDs and validates explicit requests before spawning processes.
- Defaults to leaving GPU 0 free when another GPU exists, consistent with reserving GPU 0 for the reasoning model; on a one-GPU host it falls back to that GPU.

## TRELLIS.2 / FLUX.2 notebook investigation

### Scope

Investigated the three user-requested notebooks in the OEC repository: `pipeline_trellis_3d.ipynb`, `pipeline_trellis_3d_only.ipynb`, and `pipeline_flux_only.ipynb`. Compared their setup and inference calls with the official Microsoft TRELLIS.2 and Hugging Face Diffusers sources, then reproduced image-to-3D generation through the connector-1 self-hosted runner on `scn17-mn`.

### Confirmed TRELLIS.2 inference failure

The first full image-to-3D reproduction reached the sparse-structure attention layer and failed at `xformers.ops.memory_efficient_attention`. The traceback identified that the installed xFormers extension had **no CUDA support** for the A100; its BF16 attention call offered no working operator. The notebook had installed `xformers==0.0.29.post1` with `--no-deps` while the selected PyTorch build was `2.6.0+cu124`.

Official [xFormers release history](https://github.com/facebookresearch/xformers/blob/main/CHANGELOG.md) identifies `0.0.29.post2` as the matched PyTorch 2.6.0/CUDA 12.4 wheel. Installed that wheel **only in a throwaway venv under runner temp**, validated `python -m xformers.info`, and kept the shared `phase2_3d` environment unchanged. The info report showed PyTorch `2.6.0+cu124`, CUDA `12.4`, A100 compute capability `8.0`, and `memory_efficient_attention.cutlassF-pt: available`.

A subsequent full smoke test loaded the cached official TRELLIS.2 model offline, preprocessed TRELLIS's local example image, ran actual image-to-3D inference, simplified the mesh, and exported a real GLB. Results:

- Pipeline load: pass, 142.6 s.
- Image-to-3D inference: pass, 222.0 s.
- Mesh reported 6,348,077 vertices and 13,194,108 faces before export processing.
- GLB export: pass, 108.6 s, output 8,950,028 bytes; decimation target 100,000.
- Final markers: `TRELLIS_IMAGE_TO_3D_SMOKE=PASS`, `LIVE_OEC_CHECKOUT_PRESERVED=PASS`.
- Run: [connector-1 image-to-3D + GLB smoke test](https://github.com/Killer4K-N/Connector_1/actions/runs/37942265623).
- Artifact (diagnostic log and generated GLB): [open artifact](https://github.com/Killer4K-N/Connector_1/actions/runs/37942265623/artifacts/11622412194).

The test ran with Hugging Face offline flags; it did not download model weights, start any production queue/worker, or write to the OEC production output directory. The GLB and logs were written to runner temp and uploaded as an artifact.

### Other TRELLIS loader defects fixed

The two TRELLIS notebooks passed `local_files_only=True` to `Trellis2ImageTo3DPipeline.from_pretrained()`, which does not accept that keyword. A broad `except Exception` then incorrectly reported this API error as an incomplete model cache and entered the download/storage-admission branch. The correct sequence now uses Hugging Face's `snapshot_download(..., local_files_only=True)`, resolves the real hub cache at `SYSTEM_DIRS["models"]/hub`, passes the returned **local snapshot directory** to the TRELLIS loader, and catches only `LocalEntryNotFoundError` for a genuine missing-cache fallback. Model/config/CUDA/import errors are no longer disguised as cache misses. Downloads still use the existing managed storage-admission guard and require fresh quota telemetry.

### CuMesh/export hardening

The official [TRELLIS.2 issue #84](https://github.com/microsoft/TRELLIS.2/issues/84) describes CuMesh CUDA illegal-memory-access failures during GLB atlas/export processing for low polygon targets after repeated generations; the discussion recommends updating CuMesh. The current notebook setup checked only whether CuMesh imported, so an older build could remain indefinitely.

Both TRELLIS setup cells now include a one-time, per-Python-environment install marker for official CuMesh revision `12289e1062f0603f2f0d0771b02e1395d247f26f`. It uses a versioned source-directory name instead of deleting/replacing an existing checkout, performs storage preflight with fresh quota required before compilation, and writes the marker only after a successful install. Removed the old setup path that deleted the existing `CuMesh` directory. The polygon slider is aligned to the official TRELLIS.2 range (100,000–1,000,000; default 500,000).

**Verification caveat:** the end-to-end GLB smoke run above used the already-installed CuMesh package and passed once at target 100,000. The newly pinned CuMesh source build and repeated-generation stability have not yet been end-to-end tested; the update is grounded in the upstream report but should not be presented as hardware-verified. The new build remains behind storage admission.

### FLUX.2 dependency conflict and correction

The saved FLUX notebook output showed Diffusers failing to import because its runtime check found `huggingface-hub==1.27.0` despite requiring a pre-1.0 version. The prior setup installed Diffusers from unpinned GitHub `main`, which has since advanced to `diffusers==0.41.0.dev0` and requires Hub `>=1.32.0`; that directly conflicts with `transformers==4.56.1`'s Hub `<1.0` constraint. Reproduced the resolver failure in a separate connector-1 scratch venv: [failed test using moving Diffusers main](https://github.com/Killer4K-N/Connector_1/actions/runs/37944139555).

The official [Diffusers v0.37.0 release](https://github.com/huggingface/diffusers/releases/tag/v0.37.0) contains `Flux2KleinPipeline` and its package metadata accepts Hub `>=0.34.0,<2.0` and Transformers `>=4.41.2`; that is compatible with the pinned `huggingface-hub==0.36.0` and `transformers==4.56.1`. Both the combined and FLUX-only notebooks have been changed to pin the released `diffusers==0.37.0`, validate imports including `Flux2KleinPipeline` during setup, and stop with a clear restart instruction if pip has changed Hub on disk while the currently running Jupyter kernel still holds an incompatible Hub version in memory. In the combined notebook, dependency setup is moved before loading either model.

The corrected-release scratch test completed successfully in a temporary environment: `diffusers==0.37.0`, `huggingface-hub==0.36.0`, and `transformers==4.56.1`; `DiffusionPipeline` and `Flux2KleinPipeline` both imported successfully, and the version assertions passed. Run: [FLUX dependency compatibility test](https://github.com/Killer4K-N/Connector_1/actions/runs/37944504866) · [test artifact](https://github.com/Killer4K-N/Connector_1/actions/runs/37944504866/artifacts/11623173549). No packages in the shared environment were changed by either scratch dependency test. Official references: [Diffusers 0.37.0 release](https://github.com/huggingface/diffusers/releases/tag/v0.37.0) and [v0.37.0 dependency metadata](https://github.com/huggingface/diffusers/blob/v0.37.0/setup.py).
