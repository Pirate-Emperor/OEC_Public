## 1. Research framing

OEC is a modular multimodal environment-creation and asset-production platform. It combines specialist generative models with application orchestration, resource governance, interactive presentation and artifact validation. It is not a single monolithic model.

The system-level contribution can be described through four connected capabilities:

1. **Multimodal asset synthesis:** image, 3D, video, music, environmental sound and speech generation through specialist model routes.
2. **Interactive world continuation:** extending an initial visual scene into a changing environment conditioned on player controls and prior frames.
3. **Coordinated production:** routing model outputs through workers, queues, QA and delivery stages instead of treating each model as an isolated notebook.
4. **Reproducible execution:** explicit environments, A100-aware process admission, controlled storage writes, artifact validation, metadata and run-scoped evidence.

The contribution should be framed as a system integration and engineering contribution unless a separate controlled research comparison establishes a stronger algorithmic claim. Software routing or retrieval should not be described as a trained sparse mixture-of-experts neural network.

## 2. Architecture

### 2.1 OEC-Play: prompt-to-interactive-world

**User prompt and settings → Gemma 4 E4B prompt enrichment → FLUX.2 Klein seed image → safety validation → Waypoint world-model rollout → rendered interactive frames.**

Gemma interprets and enriches scene-authoring language. FLUX generates a still starting frame or edits a reference image. That frame initializes the interactive world engine. Waypoint predicts subsequent visual frames from frame history and keyboard/mouse controls. The client renderer presents the returned frames.

The key distinction is that FLUX creates the starting image, while Waypoint performs the interactive continuation. The seed image is not itself a traversable 3D level, collision map, persistent object-state database or rigged animated character.

OEC-Play also includes scene presets and prompt authoring, visual-style/environment/atmosphere/density controls, motion/detail profiles, first-person held-item prompt directives, keyboard/mouse controls, scene editing, settings, locally synthesized ambient audio, UI sound effects and session recording. A held-item choice guides the still-image prompt; it does not guarantee a rigged 3D object or character animation.

### 2.2 OEC Core: specialist media and asset paths

- **FLUX.2 Klein 4B:** prompt-to-image generation and reference-based editing; output is a still image.
- **TRELLIS.2-4B:** image-to-3D generation; output is a GLB asset.
- **LTX-2.3:** video asset generation; output is MP4.
- **AudioGen medium:** text-conditioned environmental sound generation; output is WAV.
- **MusicGen medium:** text-conditioned music generation; output is WAV.
- **ACE-Step 1.5:** alternative music generation; output is FLAC.
- **Kokoro-82M:** text-to-speech; output is WAV.
- **Whisper Turbo and Qwen3-ASR-0.6B:** speech recognition; output is transcript text and any returned segment metadata.

The composite image-to-3D path passes the image generated by FLUX into TRELLIS and then validates the exported GLB. This is a distinct workflow from OEC-Play's still-image seed followed by interactive Waypoint rollout.

### 2.3 Orchestrated asset workflow

**Brain / configured use case → bounded prompt/job record → LTX worker → asset-status record → Qwen2-VL QA → approved upload → chunk manifest and remote read-back.**

The orchestrator, video worker, QA worker and uploader have separate responsibilities. The QA worker processes a selected asset record; the uploader is designed to consume only an approved item. Chunked read-back checks the delivered content rather than treating successful upload initiation as final acceptance.

### 2.4 Cross-cutting governance

StorageManager and process-aware GPU admission govern shared model/output operations. They provide controlled writes, reserve/quota checks, resource eligibility, runtime isolation and run-scoped evidence. Fail-closed admission prevents a denied write or ineligible GPU from being silently bypassed.

## 3. Model mechanics and application integration

### 3.1 Waypoint interactive rollout

The OEC-Play runtime wraps a world-engine interface with typed session configuration, model/backend selection, quantization capability filtering, seed-frame management and control-input messages. The client sends button and mouse-delta snapshots. The server maps these values to the engine's controller representation, generates a frame batch, preserves sequence history and returns data for rendering.

The repository's Waypoint-1.5 configuration identifies temporal compression of four frames per model step and a 720p seed/output target. The engine manager exposes an inference frame-rate cap. These are configuration/interface facts; an actual sustained FPS should be reported only from a measured runtime capture.

The application can retain session properties in video metadata and action streams as NDJSON. This enables analysis of model/seed/configuration context and relationships between player controls and generated-frame progression.

### 3.2 Scene Authoring

Scene Authoring separates semantic prompt construction from image synthesis. The prompt UI combines free text with structured modifiers. A vision-language model enriches the request into image-generation or editing instructions; FLUX generates the still image. The new frame can be safety-checked and used to initialize or update the world engine.

### 3.3 Interactive world versus conventional game simulation

The learned world model generates visual consequences conditioned on prior frames and player controls. This should be distinguished from deterministic rigid-body simulation. The analysis should separate:
- visual plausibility and temporal continuity;
- control responsiveness and camera motion;
- persistent entity/world-state logic handled by application components;
- physical collision and geometric guarantees.

Typed entity and interaction contracts add authoritative structured state for selected gameplay entities. They complement, rather than transform, the learned visual rollout into a conventional deterministic physics simulator.

## 4. Five-stage evaluation structure

The five-stage workflow is:

1. **Intent and setup:** prompt/schema validation, settings, seed and model/backend selection.
2. **Seed authoring:** prompt enrichment, image generation/editing and safety/seed handling.
3. **Interactive rollout:** frame-history-conditioned model generation and presentation.
4. **World interaction:** controls, scene events, state transitions, audio cues, pause/reset and recording.
5. **Evidence and delivery:** media-format checks, metadata, recording, logs, QA, manifest and read-back.

## 9. Dissertation-ready synthesis paragraph

OEC implements a modular multimodal environment-creation workflow connecting scene prompting, still-image synthesis, interactive world-model rollout and specialist media-generation services. The interactive application uses a language-model-assisted scene-authoring stage to refine a user's scene description, an image generator to produce the initial visual seed, and an action-conditioned world model to continue the environment during play. In parallel, the core platform provides image-to-3D conversion, video synthesis, sound-effect and music generation, text-to-speech and speech recognition. These routes are supported by typed client/server contracts, worker orchestration, controlled storage operations, process-aware GPU admission and artifact validation. Recorded engineering evidence includes an 18-notebook structural audit, a 13-interface Gradio launch sweep, a 56-test server contract suite, historical A100 inference for multiple audio/speech routes and a composite image-to-3D run that exported and structurally reopened a GLB asset. The project owner additionally confirms that subsequent local changes brought the requested OEC-Play and integrated workflows into functioning operation. Together, these results describe a practical system-level contribution: a controlled framework for combining specialist generative models into an interactive and multimodal content-production experience.
